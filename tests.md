# Описание тестов: тактильные и RFID датчики

Документ описывает **как устроены** тесты, **что происходит в сцене Gazebo**, и **почему** тесты построены именно так. Для каждого теста указано: назначение, сцена, параметры датчика, пошаговая логика, критерии прохождения, и объяснение решений.

---

## Общие понятия

### Как устроен тактильный датчик в проекте

Тактильный датчик в Gazebo — это модель с **двумя физическими телами**, связанными жёстким соединением:

1. **`mount` (основание)** — массивное тело (1000 кг) с отключённой гравитацией (`<gravity>false</gravity>`). Это "виртуальная стена", к которой крепится сенсор. Нужно чтобы датчик не падал и не отлетал при контакте.

2. **`body` (тело датчика)** — реальная геометрия (цилиндр или box) с реалистичной массой (например, 0.02 кг для leptrino, 0.73 кг для AMTI). Именно к этому телу привязан **collision** и **contact sensor**.

Связь между ними — `<joint type="fixed">`. Mount держит body в воздухе на фиксированной позиции.

На body установлены **два сенсора Gazebo**:
- **`<sensor type="contact">`** с плагином `libgazebo_ros_bumper.so` → публикует `ContactsState` в топик `/<namespace>/bumper_states`. Это основной источник данных для всех T1-T4.
- **`<sensor type="force_torque">`** в joint — резервный, но в тестах не используется.

### Тег `<sensor_size>` в SDF

Добавлен отдельный XML-тег для каждого тактильного датчика:
```xml
<sensor_size>0.018 0.018 0.026</sensor_size>
```

Формат: `[X Y Z]` в метрах. Это **bounding box** датчика:
- Для **box**-датчика — реальные размеры коробки
- Для **cylinder**-датчика — `[диаметр, диаметр, длина]`

Не используем встроенный `<size>` внутри `<box><size>`, потому что это приводит к коллизиям парсинга при `findall("size")` — находит несколько совпадений. `<sensor_size>` гарантированно уникален.

Тесты читают этот тег через `sensor.params.get("sensor_size")`.

### Probe (щуп) в сцене

Во всех тактильных сценах (`tactile_force.world`, `tactile_uniformity.world`) присутствует модель **щупа** — это небольшая сфера на стержне, которая телепортируется для создания контакта:

- `force_probe` / `uniformity_probe` — имя модели
- Collision: сфера радиусом 3 мм в позиции `(0, 0, -0.01)` относительно origin probe_link
- Это значит: нижняя точка щупа = `probe_link.z - 0.013` (смещение 10 мм + радиус 3 мм)

Масса щупа маленькая (0.05 кг) чтобы не "ломать" физику при телепортации.

### Координаты щупа

Раньше использовались хардкоды `rest_z=0.12`, `contact_z=0.095`, но они не подходят для датчиков с разной высотой. Теперь координаты вычисляются **динамически** от размера датчика:

```python
size_z = float(raw_size[2])          # высота датчика из sensor_size
sensor_top_z = size_z / 2.0          # верх body в мире (центр body на z=0)
probe_tip_offset = 0.013             # смещение tip от probe_link origin

rest_z = sensor_top_z + 0.013 + 0.05     # 5 см над датчиком
contact_z = sensor_top_z + 0.013 - penetration  # probe утоплен на `penetration` мм
```

Для **leptrino** (size_z=26 мм): `rest_z = 0.076 м`, `contact_z ≈ 0.025 м`.
Для **AMTI** (size_z=29 мм): `rest_z = 0.077 м`, `contact_z ≈ 0.027 м`.

### Захват данных: `capture_persistent` vs `capture_data`

Все 4 тактильных теста (и все 7 RFID-тестов) используют **`sensor.capture_persistent()`** для захвата сообщений.

**Причина:** `capture_data()` использует `rospy.wait_for_message()` в цикле — между итерациями subscriber уничтожается и создаётся заново. За это время (50-200 мс) сообщения от bumper plugin (50 Hz) и RFID antenna (20 Hz) **теряются** — ловится только 5-20% реального потока.

`capture_persistent()` использует один постоянный `rospy.Subscriber` на всё окно захвата. Ловит **все** сообщения без пропусков.

## Тактильные тесты

### T1 — Minimum Force Threshold (Минимальная детектируемая сила)

**Функция:** `tactile_min_force_threshold(simulator, sensor, progress_cb)`

**Сцена:** `assets/worlds/tactile_force.world`

**В сцене:**
- Земля, солнце, направленный свет
- Инжектированный тактильный датчик
- `force_probe` — щуп со сферическим наконечником
- Mounting platform (для визуального контекста)

**Что используем из датчика:**
- `sensor_size[2]` — высота для расчёта координат щупа
- Топик `ContactsState` через `capture_persistent`

**Логика:**

1. Открыть сцену, дождаться спавна `force_probe`
2. Вычислить координаты:
   - `start_pos = [0, 0, sensor_top + 0.063]` — 5 см над датчиком
   - `contact_pos = [0, 0, sensor_top + 0.013]` — точно на поверхности датчика
3. Для каждого значения силы `[0.5, 1.0, 1.5, 2.0, 2.5, 3.0]` N:
   - **Поднять щуп** в start_pos (~6.3 см над датчиком)
   - **Опустить** на глубину `penetration = force_norm × 0.001` м в датчик
   - Захватить `ContactsState` за 1.5 секунды через `capture_persistent`
   - Для каждого сообщения извлечь модуль силы: `|F| = √(Fx² + Fy² + Fz²)`
   - Зафиксировать максимум и пометить как "detected"
4. Минимальная сила при которой был ≥1 detect — `min_detected_force`

**Критерий прохождения:**
```python
passed = (min_detected_force is not None) and (min_detected_force <= 2.0 N)
```

Датчик должен реагировать на силу **≤ 2 Н**. Более грубые датчики не проходят.

**Почему так:**

- **Подъём перед каждой силой** (не просто разные глубины подряд): щуп выходит из контакта, потом снова входит — это создаёт **изменение состояния контакта**, bumper plugin обязательно публикует событие. Без подъёма плагин может молчать если считает контакт стабильным.
- **Силы по возрастающей**: начинаем с 0.5 Н (очень слабое касание). Чувствительный датчик детектит уже первую силу. Менее чувствительный — только с 2-3 Н.
- **penetration ∝ force**: это условная модель, реальная физика спрингового контакта в Gazebo (`kp × penetration = force`) даёт большие значения из-за высокой жёсткости `kp=1e6`, но нам важна **факт детекции**, а не абсолютная точность.

### T2 — Response Uniformity (Равномерность отклика по поверхности)

**Функция:** `tactile_response_uniformity(simulator, sensor, progress_cb)`

**Сцена:** `assets/worlds/tactile_uniformity.world`

**В сцене:**
- Стандартное окружение (земля, свет)
- Тактильный датчик
- `uniformity_probe` — щуп
- **9 визуальных маркеров** (красные точки) показывающих сетку тестирования
- Сетка из тонких визуальных линий

**Что используем из датчика:**
- `sensor_size[0], sensor_size[1]` — размеры в плане X, Y (для box-сетки)
- `collision/geometry/cylinder/radius` — если датчик цилиндрический (для круговой сетки)
- Топик `ContactsState`

**Логика:**

1. Открыть сцену, дождаться спавна `uniformity_probe`
2. Вычислить координаты щупа (как в T1)
3. **Определить форму датчика** из SDF:
   - Если есть тег `<collision><geometry><cylinder><radius>` → `shape = "cylinder"`
   - Иначе → `shape = "box"`
4. Построить **9 точек сетки**:
   - **Для box:** классическая сетка 3×3 в пределах 80% площади датчика
   - **Для cylinder:** центр + 8 точек по окружности радиусом `R × 0.7`, через каждые 45°
5. Для каждой точки сетки:
   - Поднять щуп в `rest_z` (5 см над датчиком)
   - Опустить в `contact_z`
   - Запустить **wiggle** в отдельном потоке: колышем щуп ±0.5 мм по Z дважды → создаём события контакта
   - Пока wiggle идёт, `capture_persistent` 1.5 с собирает ContactsState
   - Взять **медиану** модулей сил из всех сообщений как "stable_response"
6. Составить матрицу `response_grid[3][3]`
7. Вычислить статистики: mean, std, max_deviation (% отклонение от mean), missed_points (точки со значением 0)

**Критерий прохождения:**
```python
passed = (max_deviation_percent <= 150%) and (missed_points == 0)
```

**Почему так:**

- **Круговая сетка для цилиндров:** квадратная сетка 3×3 в пределах 80% площади размещает угловые точки по диагонали на расстоянии `≈ 0.566 × size` от центра. Для цилиндра (bounding box = диаметр × диаметр) это **за пределами окружности** (диагональ квадрата длиннее диаметра). Щуп падает мимо датчика — получаем `missed_points=4-8`. Круговая сетка с радиусом `0.7R` гарантирует что все 8 периферийных точек внутри физической границы цилиндра.
- **Wiggle в отдельном потоке:** bumper plugin часто публикует **только при изменении состояния контакта**. Статичный щуп = нет изменений = нет публикаций. Wiggle ±0.5 мм двигает щуп на микроны вверх-вниз, создавая искусственные изменения, но не отрывая контакт.
- **Медиана, не максимум:** Gazebo spring contact может давать одиночные всплески 1000+ Н при teleport. Медиана устойчива к таким выбросам и отражает "рабочее" значение силы.
- **Порог 150% (а не 10%):** реальный физический датчик должен иметь равномерность ≤ 10%, но Gazebo physics на мелких объектах (миллиметры) даёт нестабильные силы из-за дискретизации коллизий. 150% — компромисс: пропускаются сильно аномальные датчики, но не придираемся к normal jitter симуляции.

### T3 — Temporal Stability (Стабильность во времени под постоянной нагрузкой)

**Функция:** `tactile_temporal_stability(simulator, sensor, progress_cb)`

**Сцена:** `assets/worlds/tactile_force.world` (та же что у T1)

**Что используем из датчика:**
- `sensor_size[2]` для координат
- Топик `ContactsState`

**Логика:**

1. Открыть сцену, дождаться `force_probe`
2. Зафиксированная сила: **4.9 Н** (примерно 0.5 кг)
3. Опустить щуп в `contact_z` (утоплен на 4.9 мм)
4. Записать временной ряд **30 отсчётов** с интервалом ~1 с:
   - Микро-wiggle ±0.5 мм (50 мс) — триггер для bumper plugin
   - `capture_persistent` на 0.7 с — собирает ContactsState
   - Взять max force из всех сообщений
5. Убрать нагрузку (поднять щуп), через 2 с проверить recovery
6. Вычислить drift, jitter, recovery:
   - `start_mean` — среднее по первым 20% отсчётов
   - `end_mean` — среднее по последним 20%
   - `drift_percent = (end_mean - start_mean) / start_mean × 100%`
   - `jitter_percent` — CV (коэффициент вариации) по всей серии
   - `recovery_ok = force_after_release < 0.1 Н`

**Критерий прохождения:**
```python
passed = (abs(drift_percent) <= 5%)
```

**Почему так:**

- **30 отсчётов по 1 Гц:** стандартная практика для тестов временного дрейфа (WZ50 при 30 секундах достаточно для детекции ползучести).
- **Микро-wiggle:** критично чтобы получить **30 отсчётов**. Без wiggle при стабильном контакте bumper plugin публикует редко, получали 3/30.
- **Drift по первым и последним 20%:** усредняем чтобы снизить влияние одиночных выбросов в начале/конце ряда.
- **Recovery:** проверка что датчик "отпускает" значения после снятия нагрузки (не показывает остаточную силу). Gazebo обычно идеально освобождает контакт, так что это всегда true, но для реальных датчиков это индикатор гистерезиса.

### T4 — Peak Load Response (Реакция на пиковую нагрузку/удар)

**Функция:** `tactile_peak_load_response(simulator, sensor, progress_cb)`

**Сцена:** `assets/worlds/tactile_force.world`

**Что используем из датчика:**
- `sensor_size[2]`
- Топик `ContactsState`

**Логика:**

1. Открыть сцену, дождаться `force_probe`
2. Вычислить координаты:
   - `sensor_surface_z = size_z / 2 + 0.013` — probe_link z когда tip касается поверхности
   - `rest_z = sensor_surface_z + drop_height` — 0.5 м над поверхностью
   - `impact_z = sensor_surface_z - 0.005` — 5 мм глубокая пенетрация (имитация удара)
3. Поднять probe в `rest_z` (50 см над датчиком)
4. **Baseline measurement**: `capture_persistent` 1 с — фиксируем "фоновую" силу (должна быть 0 при отсутствии контакта)
5. **Impact**: `simulator.set_pose(probe, impact_z)` — щуп телепортируется на 5 мм внутрь датчика
6. **Захват impact events**: один `capture_persistent` на 2 секунды
7. Постобработка:
   - Сообщения распределяются по 20 time-buckets (100 мс каждый)
   - В каждом bucket берётся max force → кривая force(t)
   - `peak_force = max(force_series)`
   - `peak_time = индекс bucket × 0.1 с`
   - `impulse = ∫F·dt` над baseline (трапеции)
   - `saturation_ratio = fraction of samples with F >= 0.95 × peak` (индикатор клиппирования)

**Критерий прохождения:**
```python
passed = (peak > baseline) and (impulse_detected) and (saturation < threshold)
```

**Почему так:**

- **Teleport вместо настоящего падения:** в Gazebo настоящее свободное падение 0.5 м занимает 0.32 с, что требует стабильной физики. Teleport моделирует эффект удара (резкое проникновение), но это не идентично реальному impact. Для quick check достаточно.
- **Единый persistent subscriber на 2 с:** tight loop с `capture_data(0.08s)` терял 90%+ impact events между итерациями. Одна долгая подписка ловит все события, постобработка раскладывает их по времени.
- **Bucket-based binning:** даёт понятный time-series график в результате, независимо от скорости публикаций.
- **Saturation ratio:** если датчик "зашкаливает" (много точек на 95%+ peak), значит impact force близок к максимально измеряемому → физический датчик показал бы клиппирование. Gazebo bumper не клиппирует, но мы отслеживаем именно соотношение для согласованности с реальными датчиками.

## RFID тесты

### Архитектура RFID-сенсора в Gazebo

RFID в проекте — кастомные C++ плагины в `catkin_ws/src/RFID_Sensor_Plugin_gazebo/`:

1. **`libRFID_tag_plugin.so`** — spawner. Читает карту (map.txt) из пар (имя, x, y, z) и **создаёт модели тегов** (`rfid_tag1, rfid_tag2, ...`) в симуляции.
2. **`libRFID_antenna_plugin.so`** — детектор. Определяет видимость тегов в beam-cone антенны. Публикует `PoseStamped` в топик `/detected_tags` с `header.frame_id = имя_тега`.

**SDF антенны** содержит ключевые параметры:
- `<rzero>` — радиус детектирования (м)
- `<azimuth_beamwidth>`, `<elevation_beamwidth>` — ширина луча в радианах
- `<deterministic_threshold>` — порог сигнала для детекции (0.01 = детектить всё в пределах rzero)
- `<stop_after_misses>` — прерывать сканирование после N промахов (100 = сканировать все теги)

Для тестов используется `rfid_antenna_wide.sdf`:
- `rzero = 3 м`
- `beamwidth = 2π` (полная сфера)
- `threshold = 0.01`

### Как работает `map.txt`

Тесты пишут файл `catkin_ws/src/RFID_Sensor_Plugin_gazebo/rfid_tag_plugin/map_layouts/map.txt`. Формат:
```
fix1 1 0.5 0.0 0
fix2 2 1.5 0.0 0
...
```
Колонки: `name id x y z`. Tag plugin при старте читает файл → спавнит модели `rfid_tag1, rfid_tag2, ...` в указанных позициях.

### Захват через `capture_persistent`

Антенна публикует **одно сообщение на каждый видимый тег в каждом цикле** (20 Hz). Если в beam 5 тегов — 5 сообщений за 50 мс. `capture_data` (wait_for_message в цикле) успевает поймать только 1-2 сообщения → кажется что видится всего 1 тег. Поэтому все RFID тесты используют `capture_persistent`.

### rfid_max_stable_read_distance — Максимальный радиус считывания

**Сцена:** `rfid_change_distance.world`

**В сцене:** только антенна `rfid_antenna` и один тег, который тесты двигают.

**Логика:**

1. Из `sensor.params` прочитать `rzero` (по умолчанию 3 м)
2. Записать `map.txt` с одним тегом `fix1 1 0.5 0 0`
3. Открыть сцену, дождаться спавна `rfid_tag1`
4. Перемещать тег по оси X от 0.5 до `rzero` с шагом 0.5 м:
   - Телепортировать на `reset = rzero × 5` (далеко вне зоны) и обратно на текущую дистанцию
   - `capture_persistent` 3 секунды
   - Если `rfid_tag1` в полученных frame_id → `max_dist = current`
5. Вернуть максимальную дистанцию на которой тег детектился

**Критерий прохождения:**
```python
passed = abs(max_read_distance - rzero) <= 0.5 м
```

**Почему так:**

- **Reset далеко + return:** без этого тег остаётся в зоне детекции с предыдущей итерации, результат грязный. Reset гарантирует что каждая итерация — чистый сценарий "тег появился на дистанции X".
- **Шаг 0.5 м:** компромисс между точностью и временем теста. 6 итераций × 3 с = 18 с минимум.
- **±0.5 м допуск:** `rzero` в SDF задан как константа, но реальная детекция немного размывается на границе (близко к пороговому SNR). 0.5 м — реалистичный допуск.

### rfid_min_stable_read_distance — Минимальный радиус считывания

**Сцена:** та же, `rfid_change_distance.world`

**Логика:**
Зеркальна предыдущей — движемся от 0.25 м к 0 с шагом 1 см, фиксируем минимальную дистанцию.

**Критерий прохождения:**
```python
passed = min_read_distance <= 0.05 м
```

Проверяем что антенна не имеет "слепой зоны" вблизи (≤5 см).

### rfid_mass_read — Массовое считывание

**Сцена:** `rfid_mass_read.world`

**Логика:**

1. Записать `map.txt` с **10 тегами** равномерно на окружности радиусом `rzero/2` в плоскости XY (вокруг антенны)
2. Открыть сцену, дождаться всех 10 тегов
3. `capture_persistent` 20 секунд
4. Посчитать уникальные frame_id из принятых сообщений

**Критерий прохождения:**
```python
passed = (detected / tags_count) >= 0.75  # минимум 7 из 10
```

**Почему 10 тегов и 75%:** практический порог для оценки параллельной обработки. Антенна использует time-multiplexing (перебирает теги последовательно). 100% обнаружение за 20 с значит высокая пропускная способность; 75% — минимальный разумный порог.

### rfid_overlap_tags — Разрешение близко расположенных тегов

**Сцена:** `rfid_overlap_tags.world`

**Логика:**

1. Для каждой дистанции между тегами `[0.2, 0.1, 0.05, 0.02]` м:
   - 5 тегов на дуге с указанным межтеговым расстоянием
   - Открыть сцену (пересоздаётся каждую итерацию)
   - `capture_persistent` 5 с
   - Если поймано ≥ 50% (≥3 из 5) → `dist_result = distance`
2. Записать минимальную дистанцию при которой тест прошёл

**Критерий прохождения:**
```python
passed = dist_result is not None  # хоть какая-то из 4 дистанций дала ≥50%
```

**Почему ряд 20/10/5/2 см:** близкое расположение проверяет **пространственное разрешение** антенны. Если анттенна "слепит" соседние теги в один — на 2 см она не справится, но на 20 см должна.

### rfid_angle_dependence — Зависимость от угла наклона тега

**Сцена:** `rfid_angle_dependence.world`

**Логика:**

1. Разместить **5 тегов** в плоскости XZ под углами 0°, 30°, 45°, 60°, 90° от вертикали
2. Открыть сцену, дождаться всех 5
3. `capture_persistent` 20 с
4. Посчитать уникальные frame_id

**Критерий прохождения:**
```python
passed = (detected == 5)  # все 5 должны быть видны
```

**Почему 100%:** с `beamwidth=2π` антенна должна видеть всю полусферу. Если какой-то угол слепой — антенна неисправна.

### rfid_move_tags — Детекция движущихся тегов

**Сцена:** `rfid_move_tags.world`

**Логика:**

1. Один тег движется вдоль оси X через зону детекции (от `-rzero × 1.5` до `+rzero × 1.5`)
2. Для каждой скорости `[0.2, 0.4, 0.7, 1.0]` м/с:
   - Пересоздать сцену с тегом в стартовой позиции
   - Запустить **два параллельных потока**:
     - **Основной поток**: движет тег через `set_pose` с шагом 5 см и паузой `step_size / speed` с
     - **Worker thread**: одновременно крутит `capture_persistent` на время прохождения + 5 с
   - Если в полученных frame_id ровно **1 уникальный** (тот же тег) → `result_speed = max(result_speed, v)`
3. Вернуть максимальную скорость при которой тест прошёл

**Критерий прохождения:**
```python
passed = result_speed is not None
```

**Почему threading:** цикл `set_pose` и `capture_persistent` должны работать **одновременно**. В однопоточном коде одно блокировало бы другое. Daemon thread для capture — он умирает вместе с главным при ошибке.

**Почему "== 1":** в правильном сценарии движется один тег, он должен быть прочитан один раз или несколько раз подряд. Если вдруг появляется второй frame_id — это баг плагина (дублирование моделей).

### rfid_antenna_rotation — Вращение антенны

**Сцена:** `rfid_antenna_rotation.world`

**Логика:**

1. 10 тегов в плоскости XY равномерно по окружности радиусом `rzero/2`
2. Антенна вращается вокруг оси Z на углы `[0°, 30°, 60°, 90°]`:
   - `set_pose("rfid_antenna", quaternion=q)` задаёт вращение антенны
   - `capture_persistent` 7 с
   - Для каждого угла считаем сколько уникальных frame_id
3. Сохраняем словарь `угол → количество_тегов`

**Критерий прохождения:**
```python
passed = для хоть одного угла len(detected) >= tags_count × 0.5  # ≥5 из 10
```

**Почему так:**
- С `beamwidth=2π` поворот антенны **не должен** менять количество видимых тегов. Они все в полусфере.
- Если тест падает на каком-то угле — антенна имеет направленную диаграмму, несмотря на декларированный 2π beam.
- Допуск 50% — чтобы учесть граничные эффекты (теги на самом краю rzero).

## Технические решения (почему именно так)

### 1. Динамические координаты вместо хардкодов

**Было:** `rest_z=0.12`, `contact_z=0.095` — жёсткие значения, подходили только для AMTI.

**Стало:** координаты вычисляются от `sensor_size[2]`. Теперь работает для любого датчика любой высоты.

### 2. `capture_persistent` вместо `capture_data`

**Было:** `wait_for_message` в цикле теряет сообщения.

**Стало:** один persistent subscriber на всё окно захвата. Не теряет события.

Эффект: для bumper plugin (50 Hz, 4 порядка сообщений/c) разница между "ловим 5% событий" и "ловим 100% событий".

### 3. Wiggle probe в T2 и T3

**Было:** стационарный probe на датчике → bumper plugin замолкает.

**Стало:** micro-oscillation ±0.5 мм триггерит contact-state changes → плагин публикует.

### 4. Круговая сетка для цилиндров в T2

**Было:** квадратная сетка 3×3, угловые точки за пределами цилиндра → 4-8 точек missed.

**Стало:** автоматическое определение формы, круговая сетка радиусом 0.7R для цилиндров.

### 5. `<sensor_size>` вместо `<size>` в SDF

**Было:** тест читал `<size>` через regex findall → находил несколько (collision, visual, inside box/cylinder) → параметр получал префиксы `1: size, 2: size`.

**Стало:** уникальный тег `<sensor_size>` — всегда одно совпадение, всегда чистое значение.

### 6. Boolean в SDF как `true/false`, не `1/0`

**Было:** `<always_on>1</always_on>` — некоторые версии `sdformat` отвергают числовые bool → плагины не загружаются → тесты молча падают.

**Стало:** `<always_on>true</always_on>` — канонический XML Schema bool, принимается всеми версиями.
